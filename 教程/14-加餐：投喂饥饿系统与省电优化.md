## 一、投喂与饥饿：需求的完整拆解

收官前加的需求，原话是：「加一个点击投喂吃的效果，然后每两个小时就自己出来找吃的，或者提醒主人给他喂吃的。」把这句口语翻译成工程规格：

| 口语 | 工程规格 |
| --- | --- |
| 「点击投喂吃的效果」 | 单击宠物 → 播 eat 动画（有限循环）→ 吃完回当前状态 |
| 「每两个小时就……」 | 距上次投喂超过 2 小时 → 进入饥饿状态 |
| 「自己出来找吃的」 | 空闲时饿了 → sad 表情 + 饥饿气泡 + 随机移动讨食 |
| 「提醒主人给他喂吃的」 | 专注中饿了 → 发系统通知（但不能轰炸） |

注意最后一条的产品微妙之处：**专注中宠物不该跳出来打扰你**（这正是番茄钟产品的价值观），所以它「努力不打扰你」，只发一条克制的系统通知。这个「分场景不同行为」的设计，直接决定了代码结构。

## 二、状态归属：谁管「饿不饿」

第一个架构决策：**饥饿状态放谁身上？**

答案藏在两个类的职责划分里。PetController 管「宠物的表现」（动画、移动、气泡），AppDelegate 管「全局事实」（时间、通知、设置）。「距上次投喂 2 小时」是一个时间事实——所以**计时与判定在 AppDelegate，状态表现的分发在 PetController**。两边靠一个属性和两个回调连接：

```swift
// AppDelegate：时间事实的持有者与判定者
private static let lastFedKey = "lastFedAt"
private static let hungerThreshold: TimeInterval = 2 * 3600   // 2 小时（秒）

/// 每 30 秒检查一次宠物是否饿了
private func startHungerCheck() {
    hungerCheckTimer?.invalidate()
    hungerCheckTimer = Timer.scheduledTimer(withTimeInterval: 30, repeats: true) { [weak self] _ in
        self?.updateHungerState()
    }
    updateHungerState()
}

private func updateHungerState() {
    pet?.isHungry = Date().timeIntervalSince(lastFedAt) > Self.hungerThreshold
}
```

```swift
// PetController：拿到状态变化后决定怎么表现
var isHungry = false {
    didSet {
        guard isHungry != oldValue else { return }   // 状态没变就不动
        if isHungry {
            scheduleBeg()                 // 饿了：安排讨食
        } else {
            hungerWorkItem?.cancel()      // 喂饱了：取消讨食
            petView.updateHunger(nil)     // 撤掉气泡
        }
    }
}
```

这段代码里每一行都是前面学过的知识在值班：

- `static let` 常量：阈值这类「魔法数字」必须命名（第 01 篇）。
- `Timer` 常驻 + 轮询：不需要精确到秒的判定，30 秒查一次绰绰有余，比「精确闹钟」简单一百倍。
- `Date().timeIntervalSince(lastFedAt)`：两个时刻相减得秒数（第 11 篇的日期计算同款）。
- `didSet` 属性观察器：值一变自动触发表现逻辑（第 10 篇的设置项同款）。
- `guard isHungry != oldValue`：只在变化时行动（第 08 篇 setPhase 同款礼仪）。

而 `lastFedAt` 本身的读写封装是另一个 Swift 小知识：

```swift
private var lastFedAt: Date {
    get {
        let ts = UserDefaults.standard.object(forKey: Self.lastFedKey) as? TimeInterval
        return ts.map(Date.init(timeIntervalSince1970:)) ?? Date()
    }
    set {
        UserDefaults.standard.set(newValue.timeIntervalSince1970, forKey: Self.lastFedKey)
    }
}
```

**计算属性 + UserDefaults 的组合**：对外表现得像普通属性（`lastFedAt = Date()`），对内每次读写都落盘。进程重启后投喂记录不丢。`?? Date()` 的默认值很妙：从没喂过 → 视为「刚刚喂过」（现在才出生，当然不饿）——首次启动不会让宠物一睁眼就讨饭。

## 三、投喂：打断与恢复的艺术

`feed()` 是 PetController 里最忙的方法，因为它要处理「宠物正在做任何事时被喂」的所有组合：

```swift
/// 投喂：打断当前动作，播放吃动画，吃完回状态
func feed() {
    guard !isPlaying(.eat) else { return }     // 正在吃就别重复喂
    hungerWorkItem?.cancel()                    // 取消排队中的讨食
    hungerBubbleWorkItem?.cancel()              // 撤讨食气泡
    petView.updateHunger(nil)
    // 打断移动
    if roamAnim != nil {
        roamAnim?.invalidate()
        roamAnim = nil
        roamFrom = nil
        roamTo = nil
        onArriveMove = nil
    }
    petView.bounce()
    petView.showHearts(count: 3)
    play(.eat) { [weak self] in
        guard let self else { return }
        self.onFed?()                            // 告诉 AppDelegate：重置饱腹计时
        if self.isSessionActive() {
            self.play(self.inRestSession ? .sleep : .focus)   // 吃完回会话状态
        } else if self.isPlaying(.eat) {
            self.play(.idle)                     // 吃完回待机
        }
    }
}
```

拆解它的动作序列：

1. **防御**：正在吃就忽略（防抖）；取消所有讨食相关任务。
2. **打断**：如果在移动，拆掉移动定时器并清掉所有移动状态（包括 `onArriveMove`——庆典移动被打断时不能到了「目的地」还触发改庆祝）。
3. **仪式感**：弹跳一下 + 飘 3 颗爱心——食物是幸福的（复用第 07 章的爱心粒子，白捡的仪式感）。
4. **吃完收尾**（completion 回调）：先通知 AppDelegate 重置计时，再根据**当前场景**决定回哪个动画——会话中回 focus/sleep，空闲回 idle。

最后那个 completion 里有个一眼看不太懂、实则精妙的守卫：

```swift
} else if self.isPlaying(.eat) {
    self.play(.idle)
}
```

为什么是 `isPlaying(.eat)`？想象这个时序：宠物还在吃，用户开始了专注 → `onSessionStart` 把它切到 focus 动画 → eat 播完的 completion 触发。如果没有这层检查，它会**把专注中的宠物拉回 idle**——bug。有了这层检查：「只有当我还停留在 eat 动画（没人打断我）时才回 idle」，优雅地免除了时序竞争。

「吃完回哪个状态」不由 feed 自己记住「吃之前是什么」，而是**吃完那一刻重新查询全局状态**（`isSessionActive()` / `inRestSession`）。这是与第 08 章热键同一招：不问历史，只查现状。状态机的状态是唯一的真相源，记住它比自己记一份「之前的动作」可靠得多。

## 四、讨食：分场景的两种剧本

饿了的宠物不会一直讨，而是每隔随机一段时间「提醒一次」，由 `scheduleBeg` 排班：

```swift
/// 排下一次讨食
private func scheduleBeg(delay: TimeInterval? = nil) {
    hungerWorkItem?.cancel()
    let wait = delay ?? Double.random(in: 60...180)   // 每 1~3 分钟提醒一次
    let item = DispatchWorkItem { [weak self] in
        self?.begForFood()
    }
    DispatchQueue.main.asyncAfter(deadline: .now() + wait, execute: item)
    hungerWorkItem = item
}
```

讨食剧本在 `begForFood()` 里分场景：

```swift
private func begForFood() {
    guard isHungry, !isPlaying(.eat) else { return }
    scheduleBeg()                       // 先排下一次（无论这次讨没讨成）
    if isSessionActive() {
        onHungryDuringSession?()        // 专注中：只发通知，不闹
        return
    }
    // 空闲：委屈表情 + 气泡 + 四处找吃的
    play(.sad) { ... 回 idle ... }
    petView.updateHunger("我饿了，点击喂我 🍖")
    // 8 秒后自动撤气泡
    ...
    performRoam()                       // 饿得四处乱走
}
```

两个设计细节：

1. **先排下一次再讨这次**。如果讨食中途被打断（比如用户正好点了投喂），下一次提醒照样在队列里，讨食节拍不断。
2. **专注中的通知有独立节流**（AppDelegate 侧）：

```swift
/// 专注中饿了：发系统通知提醒（30 分钟最多一条，避免轰炸）
private func notifyHungryThrottled() {
    if let last = lastHungerNotifyAt, Date().timeIntervalSince(last) < 1800 { return }
    lastHungerNotifyAt = Date()
    notify(title: "\(settings.currentPetName)饿了 🍖",
           body: "它正在努力不打扰你，结束后记得点击它喂点吃的～")
}
```

注意节流**放在 AppDelegate 而不是 PetController**——因为「通知」是 AppDelegate 的职责。PetController 只知道「饿了想提醒」，至于怎么提醒、提醒多少次，不归它管。分层又一次挡住了复杂度。

## 五、省电优化：三层防线

桌面宠物是常驻进程，用户开着它工作一整天。动画没做好，CPU 占用能到 5%~10%，风扇嗡嗡叫——产品立刻被判死刑。FocusPet 的省电是**三道层层递进的防线**：

### 防线一：没变化就不重绘（PetView 内）

第 05 篇讲过的核心机制，这里值得从省电角度再强调一次：

```swift
// 省电：画面内容没变就不重绘（静止帧 / 未到下一帧时刻）
if frameIndex != drawnFrameIndex {
    drawnFrameIndex = frameIndex
    needsDisplay = true
}
```

`needsDisplay = true` 是整个绘制系统的「油门」——不设它，`draw(_:)` 一次都不会执行。序列帧动画的帧率是 0.28 秒一帧，意味着**每秒钟最多重绘 3~4 次**，其余时间即使 DisplayLink 在跑，视图纹丝不动。对比 naive 实现（每帧都重绘 = 120Hz 满血刷），CPU 占用差一个数量级。

### 防线二：没活干就不派活（DisplayLink 层）

DisplayLink 在独立线程以屏幕刷新率（120Hz）回调——回调本身也有成本。所以回调第一关：

```swift
guard view.hasPendingWork(at: now) else { return kCVReturnSuccess }
```

```swift
/// 指定时刻是否有画面要变：到下一帧时刻 / 弹跳中 / 爱心飘浮中
private func hasPendingWork(at now: CFTimeInterval) -> Bool {
    if !frames.isEmpty && !finished {
        return now >= frameStartTime + frameDurations[frameIndex]
    }
    return bounceT0 != nil || !hearts.isEmpty
}
```

没到下一帧的时刻、没有弹跳、没有爱心 → 连 `DispatchQueue.main.async` 都不派发。120Hz 的回调大多在独立线程里直接返回，主线程零打扰。

### 防线三：彻底歇业（窗口隐藏时）

```swift
/// 窗口隐藏时调用：彻底暂停渲染省电
func pauseRendering() {
    stopDisplayLink()
}

/// 窗口重新显示时调用：有未完成动画则恢复刷新
func resumeRendering() {
    if !finished || bounceT0 != nil || !hearts.isEmpty {
        startDisplayLink()
    }
}
```

菜单里有「显示/隐藏宠物」开关。隐藏时不是「画一张静止图」，而是**直接把 DisplayLink 停掉**——线程回调归零，CPU 占用趋近于零。重新显示时如果动画早已播完（idle 无限循环除外，它在播），甚至不需要重启 DisplayLink。

### 防线之外：两个习惯

- **Release 构建**。Debug 版不做编译优化，同一份代码 CPU 占用可能高 2~3 倍。自己日常用也必须 `swift build -c release`（第 13 篇）。
- **定时器的节制**。项目里所有 Timer（乱窜调度、移动动画、饥饿检查）都是「要么不建、建了就按需触发」，没有一个是无意义空转的。

用活动监视器验证效果： release 版 FocusPet 日常 CPU 占用通常在 0%~1% 之间浮动——对一颗常驻桌面的小宠物来说，这就是合格的数字。

最重要的是那几条超越本项目的通用心法：

1. **状态机思维**——任何有「状态」的功能，先画状态图再写代码。
2. **回调解耦**——零件报事实，装配做决定。
3. **只在变化时行动**——不重绘、不通知、不算账。
4. **优雅降级**——读不到就当空的，没授权就静默，缺文件不崩溃。
5. **用真实代码当教材**——这套教程里每一行代码都能在项目里找到出处。
