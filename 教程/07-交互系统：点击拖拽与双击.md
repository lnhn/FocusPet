# 07 · 交互系统：点击、拖拽、双击

> FocusPet 零基础开发教程 · 第 7 篇
> 对应源码：`Sources/FocusPet/PetView.swift`（第 117–131、425–467 行）

上一篇讲完了宠物自己怎么动，这一篇讲**你怎么摆弄它**。本章要实现的交互有四个：

| 交互 | 触发方式 | 效果 |
| --- | --- | --- |
| 拖拽 | 按住宠物拖动 | 宠物跟着鼠标走，被抓起时是 wave 表情 |
| 单击 | 点一下 | 投喂（后来加的喂食功能） |
| 双击 | 快速点两下 | 庆祝 + 爱心飘出 |
| 右键 | 点鼠标右键 | 弹出系统菜单 |

听起来简单？这一章是**踩坑密度最高**的一章，三个经典的 mac 交互陷阱都会遇到。我们边写边踩。

## 一、mac 鼠标事件的来龙去脉

当你在 mac 上按一下鼠标左键，系统会产生一连串事件，按时间顺序进入你的窗口：

```
mouseDown(按下) → mouseDragged(拖动，可有多个) → mouseUp(抬起)
```

你的 `NSView` 子类可以通过覆写这些方法来响应。测试一下，在 PetView 里加一个临时打印：

```swift
override func mouseDown(with event: NSEvent) {
    print("按下了！位置: \(event.locationInWindow)")
    super.mouseDown(with: event)
}
```

`event.locationInWindow` 是这次点击在窗口坐标系里的位置——以后写拖拽都要靠它算偏移。

还有一个前置问题：无边框的 `NSPanel` 默认有个怪癖——**窗口非激活状态下，第一下点击只负责激活窗口，会被它吞掉**。用户盯着宠物发呆半天，第一次伸手去点，竟然没反应！解决办法是一行：

```swift
/// 无边框面板里的第一下点击也要能被接住
override func acceptsFirstMouse(for event: NSEvent?) -> Bool { true }
```

这行的意思是：「别管窗口激不激活，第一次点击直接给我」。

## 二、拖拽：performDrag 的零延迟魔法

### 2.1 第一版（错误示范）：跟着事件走

直觉的拖拽写法是在 `mouseDragged` 里不停地把窗口挪过去：

```swift
// ❌ 反例：别学这个
override func mouseDragged(with event: NSEvent) {
    let newOrigin = ...  // 用当前位置 + 本次位移算出窗口新位置
    window?.setFrameOrigin(newOrigin)
}
```

这个写法功能上没问题，但**手感很差**：拖动时宠物会有一种「跟不上鼠标」的粘滞感。原因在源码注释里写得很清楚：

> 那条路径走事件队列，主线程被动画绘制占住时会跟不上光标（宠物被甩在鼠标后面）。

事件队列的完整链路是：硬件产生移动 → WindowServer 派发事件 → 事件进入队列等待 → 主线程从队列里取事件 → 调用你的 `mouseDragged`。链路一长，动画线程一忙，宠物就落后鼠标半拍。

### 2.2 正确姿势：把窗口交给 WindowServer

mac 提供了一个专门的 API：

```swift
window?.performDrag(with: event)
```

它的语义是：「**从现在起，这个窗口的纹理直接由 WindowServer 跟随光标拖动**，不再经过任何事件队列」。WindowServer 是系统的窗口合成进程，它直接拿硬件光标的坐标，所以窗口跟随是**零延迟**的，任何应用代码都无法与之竞争。

这也是源码里的那段注释要刻进骨头的原因：

```swift
// 注意：不要再覆写 mouseDragged 手动 setFrameOrigin —— 那条路径走事件队列，
// 主线程被动画绘制占住时会跟不上光标（宠物被甩在鼠标后面）。
```

### 2.3 performDrag 的阻塞特性

`performDrag` 还有一个重要性质：**它会一直阻塞，直到鼠标抬起才返回**。这意味着你把按下、拖动、抬起三个阶段全包在一个函数里写：

```swift
override func mouseDown(with event: NSEvent) {
    isBeingDragged = true
    onDragPickup?()                 // 被抓起：切表情
    let originBefore = window?.frame.origin
    window?.performDrag(with: event) // ← 卡在这里，鼠标抬起才往下走
    onDragPutDown?()                // 松手落地
    isBeingDragged = false
    // ……这里还能判断「拖了多远」
}
```

这种阻塞式 API 在 Swift 里不常见（我们习惯了回调和 async/await），但它在「按下-拖动-抬起」这种天然有边界的事件流里非常好用——逻辑天然按时间顺序排好，不用维护任何状态。

「被抓起时切表情」是用一个回调挂上去的（PetView 自己不决定玩什么动画，把决定权交给 PetController）：

```swift
/// 被抓起 / 被放下（由 PetController 接上对应表情）
var onDragPickup: (() -> Void)?
var onDragPutDown: (() -> Void)?
```

而 `isBeingDragged` 标志位则是给第 06 篇的乱窜调度器看的：宠物正在被你拎着，不能一边被拎一边乱跑，所以调度器每轮决策前都要检查这个标志。

## 三、单击与双击的战争

### 3.1 冲突在哪

单击是投喂，双击是庆祝。问题是：**双击在物理上就是两次单击**。系统怎么区分你的意图？

mac 的做法是：按下后等待一个「双击判定间隔」（系统设置里可调，默认约 0.25 秒），如果这段时间内没有第二次按下，才算单击；否则两次一起算双击。

这给程序员带来一个两难：

- 如果按下就立刻触发单击 → 用户双击时会被投喂两次，且第一次投喂的动画会干扰第二次
- 如果永远等双击判定 → 单击的响应被拖慢 0.25 秒，手感迟钝

我们的解法是**延迟确认**：

```swift
/// 单击判定窗口：按下到抬起间隔太短会被双击判定点干扰，延迟确认
private var tapWorkItem: DispatchWorkItem?
```

### 3.2 clickCount：系统已经帮你数好了

`NSEvent` 自带一个 `clickCount` 属性：第一次按下它是 1，双击的第二次按下它是 2。所以在 `mouseDown` 里一行就能分流：

```swift
override func mouseDown(with event: NSEvent) {
    // 双击：触发互动，不进入拖拽；同时取消刚排队的单击（避免双击变两次投喂）
    if event.clickCount >= 2 {
        tapWorkItem?.cancel()   // 把还在排队等确认的单击取消掉！
        tapWorkItem = nil
        onDoubleTap?()
        return
    }
    // ……单击/拖拽逻辑
}
```

那句 `tapWorkItem?.cancel()` 是整个防误触的关键：**双击发生时，第一次按下时排队的那个「延迟确认单击」任务还在调度队列里等着执行，必须先取消它**，不然就会「双击 = 一次投喂 + 一次庆祝」。

### 3.3 DispatchWorkItem：可以取消的定时任务

确认单击用的是 GCD 的延迟执行：

```swift
// 原地单击（几乎没拖动）→ 延迟确认投喂，给双击判定留窗口
if let before = originBefore, let after = window?.frame.origin,
   hypot(after.x - before.x, after.y - before.y) < 6 {
    tapWorkItem?.cancel()
    let item = DispatchWorkItem { [weak self] in
        guard let self, !self.isBeingDragged else { return }
        self.onTap?()
    }
    DispatchQueue.main.asyncAfter(deadline: .now() + 0.28, execute: item)
    tapWorkItem = item
} else {
    tapWorkItem?.cancel()
    tapWorkItem = nil
}
```

逐行拆：

| 代码 | 作用 |
| --- | --- |
| `hypot(after.x - before.x, after.y - before.y) < 6` | 用位移距离区分「单击」和「拖了一下」：抬起时如果挪了不到 6 个点，算单击 |
| `DispatchWorkItem { ... }` | 把一段代码包成一个「可取消的任务对象」 |
| `DispatchQueue.main.asyncAfter(deadline: .now() + 0.28, execute: item)` | 0.28 秒后**在主线程**执行这个任务 |
| `tapWorkItem?.cancel()` | 任务还没执行就取消它——这就是双击救场的按钮 |

为什么选 0.28 秒？系统的双击判定间隔通常在 0.25 秒左右，留 0.28 秒让第二次按下来得及取消第一次排队的任务；又不会让用户等太久，单击手感依然轻快。

工作项里的双重保险也值得一提：

```swift
guard let self, !self.isBeingDragged else { return }
```

`[weak self]` 防止视图被销毁后任务还强引用着它（内存泄漏的常规防御）；`!self.isBeingDragged` 则是一个边角情况：理论上 0.28 秒内用户不可能既拖完又等任务执行，但加了这层判断，即使发生了也不会在拖拽中途误投喂。

**注意一个顺序细节**：`performDrag` 返回之后我们才做单击判定——因为距离（before/after）只有等拖完才知道。整个 `mouseDown` 方法把按下、拖动、抬起、延迟判定串成了教科书级的顺序逻辑，全靠 `performDrag` 的阻塞特性。

## 四、右键

右键反而最简单，一行回调透传出去：

```swift
override func rightMouseDown(with event: NSEvent) {
    onShowMenu?(event)
}
```

为什么是回调而不是直接在这里建菜单？因为「菜单里有什么」是应用层的事——设置入口、切换宠物、退出——这些属于 AppDelegate 的职责。PetView 只负责「有人右键了」这个事实。这种「视图报事件、上层做决定」的分层，在整套项目里反复出现（后面讲 FocusEngine 回调时你会再次见到）。

## 五、四种交互的全景

把四种交互的判定方式排在一起，这张表值得收藏：

| 交互 | 判定依据 | 关键 API | 踩过的坑 |
| --- | --- | --- | --- |
| 拖拽 | 按下后位移超过 6 点 | `window.performDrag` | 手动 `setFrameOrigin` 走事件队列会卡顿 |
| 单击 | 位移 < 6 且 0.28 秒内无第二击 | `DispatchWorkItem` + `asyncAfter` | 不延迟确认会被双击误触发 |
| 双击 | `event.clickCount >= 2` | 取消 `tapWorkItem` | 双击前必须先取消排队中的单击 |
| 右键 | `rightMouseDown` 回调 | `onShowMenu?()` | — |

加上 `acceptsFirstMouse` 和 `isBeingDragged` 这两个辅助件，整个交互系统的状态流转如下：

```
mouseDown
  ├─ clickCount ≥ 2 → 取消单击任务 → onDoubleTap（爱心庆祝）
  └─ clickCount = 1 → isBeingDragged = true → onDragPickup（被抓起表情）
        ↓
   performDrag（窗口零延迟跟手，调度器避让）
        ↓
   抬起 → onDragPutDown → isBeingDragged = false
        ├─ 位移 < 6 → 0.28s 后确认 → onTap（投喂）
        └─ 位移 ≥ 6 → 什么都不做，就是拖了个位置
```

## 练习

1. 把确认单击的延迟从 0.28 改成 0.15 秒，多双击几次，感受误触率的变化；再改成 0.5 秒，感受单击的迟钝。
2. 在 `mouseDown` 里加一句 `print(event.clickCount)`，观察单击、双击、三击时这个数字各是多少。
3. 尝试给宠物加「三击彩蛋」：三击时切换成 sleep 动画。提示：`clickCount` 会一直往上数。
4. 思考题：为什么拖拽判定的阈值是 6 而不是 0？如果设成 0，鼠标最轻微的一抖会发生什么？（答案和「双击判定」有关。）
