# 08 · 番茄钟引擎：状态机思维

## 一、什么是状态机

状态机（State Machine）一点也不玄，它回答的问题就一句话：

> **「现在处于什么状态？每个状态允许做哪些事？」**

拿电梯想：电梯只有「开门、关门、上行、下行、停止」几个状态，每个状态下只接受特定的操作——门开着的时候不可能接受「上行」指令。番茄钟也一样，它的状态图是一张有限的小地图：

```
              startFocus()                startRest()
   ┌──────┐ ─────────────→ ┌────────┐ ─────────────→ ┌──────────────┐
   │ idle │                │running │                 │短休 / 长休   │
   └──────┘ ←───────────── └────────┘ ─────────────→ └──────────────┘
              休完回 idle      │   ▲                        (也是一种
                              │   │                          running)
                    pause()   │   │  resume()
                              ▼   │
                          ┌─────────┐
                          │ paused  │
                          └─────────┘
```

对照 `FocusEngine` 里的枚举，一字不差：

```swift
enum Phase {
    case idle      // 空闲
    case running   // 倒计时中
    case paused    // 暂停（冻住剩余时间）
}
```

还有会话类型的枚举：

```swift
enum Kind: String {
    case focus
    case shortRest
    case longRest

    var isRest: Bool { self != .focus }
}
```

设计状态机时最重要的一步是**穷举状态**和**规定转移**。看 `pause()` 的第一行：

```swift
func pause() {
    guard phase == .running else { return }   // 只有 running 才能暂停
    setPhase(.paused)
}
```

`guard` 做「非法操作直接拒绝」——空闲时按快捷键，什么都不会发生，而不是冒出奇怪行为。状态机的价值就体现在这里：**它让每个非法操作都有明确的归宿（被忽略），而不是产生未定义行为**。

经典番茄钟规则：每完成 4 个专注，来一次 15 分钟长休，其余都是 5 分钟短休。这个规则在 `startRest()` 里就一行：

```swift
/// 按「已完成专注数」决定短休还是长休（每 focusesPerCycle 轮一次长休）
func startRest() {
    let isLong = completedFocuses > 0 && completedFocuses % focusesPerCycle == 0
    start(session: Session(
        kind: isLong ? .longRest : .shortRest,
        duration: isLong ? longRestDuration : shortRestDuration
    ))
}
```

`%` 是取余运算符：`completedFocuses % 4 == 0` 意为「完成的专注数是 4 的倍数」。第 01 篇语法篇讲过它，这里就是它的实战。

## 二、回调：纯逻辑引擎与 UI 的分界线

打开 `FocusEngine.swift` 看一眼——这个文件**从头到尾没有 import AppKit，没有一行 UI 代码**。这是刻意的设计：

> 纯逻辑不碰 UI。

引擎只负责计算，怎么把结果呈现出来（气泡里显示 24:59？状态栏图标变红？宠物切 focus 动画？）它一概不管。双方靠四个回调沟通：

```swift
/// 每秒回调一次剩余秒数
var onTick: ((TimeInterval) -> Void)?
/// 运行/暂停/空闲 切换
var onPhaseChange: ((Phase) -> Void)?
/// 新会话开始
var onSessionStart: ((Session) -> Void)?
/// 会话自然走完（专注/休息完成）
var onSessionComplete: ((Session) -> Void)?
```

回调就是「留个电话号码给我，有情况我打给你」。AppDelegate 在组装时把号码填上：

```swift
// 伪代码，展示接线方式
engine.onTick = { remaining in
    petView.updateTime(format(remaining))      // 气泡显示倒计时
    statusBar.updateTitle("🐱 \(format(remaining))")
}
engine.onSessionComplete = { session in
    // 宠物跑屏幕中央庆祝 + 弹系统通知 + 写统计记录
}
```

注意回调都是 `Optional`（类型后面带 `?`），调用时要写问号：

```swift
self.onTick?(self.remaining)
```

含义是「号码留了才打，没留就跳过」。这带来一个巨大的好处：**FocusEngine 可以在没有任何 UI 的单元测试里独立运行**——这是专业代码与玩具代码的分水岭之一。

这个模式在项目中反复出现，给它起个名字记牢：**好莱坞原则**（"Don't call us, we'll call you"）——引擎不主动去找视图，而是视图把回调留给引擎。

## 三、Timer：常驻 + 闸控，防漂移的巧思

### 3.1 两种暂停设计

倒计时每秒走一格，朴素的想法是「暂停就把 Timer 销毁，恢复再建一个」：

```swift
// ❌ 朴素但有隐患的写法
func pause() {
    timer?.invalidate()   // 销毁
    timer = nil
}
```

隐患在哪？`Timer.scheduledTimer(withTimeInterval: 1, ...)` 的触发时刻是相对「创建时刻」的。销毁再重建，新 Timer 的第一秒是从「创建」开始算，而不是从「恢复」那一瞬间精确对齐，多次暂停恢复后，**倒计时会慢慢漂移**（比如 25 分钟的专注实际过了 25 分 07 秒）。

### 3.2 我们的方案：Timer 一直活着，闸门控制

看 `start(session:)` 里 Timer 的闭包：

```swift
// 暂停时不倒计时，所以 timer 常驻、闸控即可，避免暂停/恢复计时漂移
timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
    guard let self, self.phase == .running else { return }   // ← 闸门
    self.remaining = max(0, self.remaining - 1)
    self.onTick?(self.remaining)
    if self.remaining <= 0 {
        self.completeSession()
    }
}
```

每秒 Timer 照常在响，但闭包第一行先检查 `phase == .running`——**暂停期间，Timer 响归响，剩余时间纹丝不动**。恢复时也不需要重建任何对象，下一秒的滴答自然继续。Timer 的触发节拍完全不受暂停影响，漂移问题被根除。

这个技巧叫**「常驻 + 闸控」（always-on with gating）**，在工程上非常常见：让节奏源保持稳定，用状态标志位决定「这一拍要不要生效」。

闭包里还有两个细节：

- `[weak self]`：又是它。Timer 会强引用这个闭包，闭包如果强引用 self（引擎），引擎就永远不能被释放——循环引用。`weak` 打破这个环。`guard let self` 把弱引用变回强引用供本次使用。
- `max(0, self.remaining - 1)`：防御性编程，保证剩余时间永不为负（虽然后面的 `<= 0` 判断已经兜底，双保险不亏）。

### 3.3 完成一次会话

```swift
private func completeSession() {
    stopTimer()
    guard let finished = session else { return }
    if finished.kind == .focus {
        completedFocuses += 1     // 只有「专注」走完才计数，休息不算
    }
    session = nil
    remaining = 0
    setPhase(.idle)
    onSessionComplete?(finished)
}
```

这里藏着一条产品规则：**只有专注走完才计入 completedFocuses**（中断放弃的不算，看 `stop()` 就知道——它直接清场，不动计数器）。所以那个「每 4 次长休」的规则天然只统计「货真价实完成的专注」。

## 四、setPhase 的小细节：只在变化时通知

```swift
private func setPhase(_ newPhase: Phase) {
    guard phase != newPhase else { return }   // 状态没变就不通知
    phase = newPhase
    onPhaseChange?(newPhase)
}
```

为什么要多这层判断？假想没有它：空闲时用户连按五次快捷键，`pause()` 的 guard 会挡住非法转移，但 `stop()` 这类方法每次都调用 `setPhase(.idle)`——没有这层判断，就会重复触发五次 `onPhaseChange`，上层收到五次「回到空闲」的通知，菜单重建五次。**「只在变化时通知」是观察者模式的通用礼仪。**

枚举的相等比较（`phase != newPhase`）之所以能直接用 `==`，是因为 Swift 的枚举自动获得相等性——不需要你手写比较逻辑。

## 五、配置即属性

引擎的四个参数是普通属性，随时可改：

```swift
var focusDuration: TimeInterval      // 默认 25 * 60 秒
var shortRestDuration: TimeInterval  // 默认 5 * 60
var longRestDuration: TimeInterval   // 默认 15 * 60
var focusesPerCycle: Int             // 默认 4
```

用户在设置面板里把专注改成 45 分钟，改的就是这里的 `focusDuration`。下一次 `startFocus()` 自然生效，不用重启、不用刷新——因为 `start(session:)` 每次都用**当前**配置值新建会话。

默认值在构造函数里给：

```swift
init(
    focusDuration: TimeInterval = 25 * 60,
    ...
) {
    self.focusDuration = focusDuration
    ...
}
```

`TimeInterval` 就是 `Double` 的别名（秒数），`25 * 60` 算出 1500 秒。用乘法写比直接写 1500 的可读性好得多——读者一眼知道是「25 分钟」。

## 六、把 141 行装进脑子

最后用一个表格总结 FocusEngine 的公共 API，这就是它的全部对外面孔：

| 方法/属性 | 状态要求 | 干什么 |
| --- | --- | --- |
| `startFocus()` | 任意（会停掉旧会话） | 开始一段专注 |
| `startRest()` | 任意 | 按完成数自动选短休/长休 |
| `pause()` | running | 暂停（闸控，不杀 Timer） |
| `resume()` | paused | 继续 |
| `stop()` | 任意 | 提前结束，不计完成数 |
| `onTick / onPhaseChange / onSessionStart / onSessionComplete` | — | 四个回调插槽 |

回想第 03 篇的类分工地图：FocusEngine 是这个项目里「纯度」最高的一个类——**没有 UI 依赖、没有单例、状态全靠自己、靠回调对外**。以后你自己写任何「计时/流程」类功能（比如闹钟、游戏回合、下载重试），都可以照抄这个骨架：枚举定义状态 → 方法控制转移（guard 拦截非法转移）→ 回调通知外界。
