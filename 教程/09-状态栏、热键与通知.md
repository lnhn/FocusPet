# 09 · 状态栏图标、全局快捷键与系统通知

> FocusPet 零基础开发教程 · 第 9 篇
> 对应源码：`Sources/FocusPet/StatusBarController.swift`（36 行）、`Sources/FocusPet/HotkeyManager.swift`（70 行）、`Sources/FocusPet/AppDelegate.swift`（通知与热键接线部分）

一个没有 Dock 图标、没有主窗口的菜单栏应用，和用户沟通的三个通道是：状态栏图标、全局快捷键、系统通知。本章把这三个小零件一次讲完——它们每一个都藏着至少一个真实的坑。

---

## 一、状态栏图标

### 1.1 最小骨架

mac 的状态栏图标官方叫 **Status Item**。最小的代码三行：

```swift
let statusItem = NSStatusBar.system.statusItem(withLength: NSStatusItem.variableLength)
statusItem.button?.title = "🐱"      // 用 emoji 当图标
statusItem.button?.action = #selector(handleClick)
```

FocusPet 里把它包成了一个 36 行的类（`StatusBarController`）。第一行值得细看：

```swift
private let statusItem = NSStatusBar.system.statusItem(withLength: NSStatusItem.variableLength)
```

- `NSStatusBar.system`：系统状态栏的单例。
- `statusItem(withLength:)`：申请一个位置。`variableLength` 表示「宽度随内容自适应」——因为我们要在图标旁边显示倒计时文字（`🐱 24:59`），宽度会变。如果内容固定可以传一个具体点数。
- 申请到的是一个 `NSStatusItem`，它内部有个 `button`（就是你在菜单栏看到的那个可点区域）。

为什么 `button` 后面要跟问号？因为理论上申请可能失败、button 可能为 nil。Swift 的可选链语法：`a?.b` 表示「a 不是 nil 才取 b，是 nil 就整句静默跳过」——这比满地 if-let 写起来轻快，适合这种「失败也无所谓」的赋值场景。

### 1.2 一个史诗级大坑：accessory 应用点图标没反应

这是本项目开发过程中真实踩过的坑，用户也反馈过「点击状态栏图标好像没啥用」。症状：点击图标，菜单偶尔弹出、偶尔没反应，弹出了也点不动里面的项。

根源藏在应用类型的选择里。FocusPet 是菜单栏应用，`Info.plist` 里设置了：

```xml
<key>LSUIElement</key><true/>
```

这让应用成为 **accessory（附属）应用**：不显示在 Dock，不出现在 ⌘Tab 切换列表。副作用是——**这类应用默认永远不成为「活跃应用」**。而菜单弹出后要接收你的点击，系统要求「菜单所属的应用是活跃的」。矛盾就此产生：点了图标 → 菜单弹出 → 应用却不活跃 → 点击事件被拒之门外。

注释里记录了教训：

```swift
/// 关键：先激活应用（accessory 模式默认不激活），
/// 否则菜单弹出后可能收不到点击、设置/统计窗口也可能不显示
NSApp.activate()
menu.popUp(
    positioning: nil,
    at: NSPoint(x: 0, y: button.bounds.height),
    in: button
)
```

`NSApp.activate()` 就是把应用临时拉回「活跃」状态。顺序不能反：先激活，再弹菜单。这个坑在 Stack Overflow 上常年霸榜，无数菜单栏应用作者都栽过。

### 1.3 为什么每次点击都重建菜单

注意这个回调的签名：

```swift
/// 点击时由 AppDelegate 重新构建菜单
var onRebuildMenu: (() -> NSMenu)?
```

点一次图标就构建一次菜单？看起来浪费，其实必要。因为菜单内容**时刻在变**：专注中菜单应显示「暂停/放弃」，空闲时应显示「开始专注」，倒计时数字也要实时。与其维护一套「增量更新菜单项」的复杂机制，不如每次点击时按当前状态从头构建一份——构建一份菜单的开销微乎其微，换来的却是「菜单永远和状态同步」的简单保证。

另外一行也值得说：

```swift
statusItem.button?.sendAction(on: [.leftMouseDown, .rightMouseDown])
```

默认只有鼠标抬起（up）才触发 action，改这行让它在**按下**瞬间触发——菜单弹出的响应更快，更有「跟手」感。

## 二、全局快捷键：按 ⇧⌘P 就能开始专注

### 2.1 为什么走 Carbon 而不是 SwiftUI

你可能听过 `KeyboardShortcuts` 之类的 Swift 库。我们用的是更底层的 **Carbon** 事件 API（`RegisterEventHotKey`），原因写在注释里：

```swift
/// 全局快捷键（Carbon RegisterEventKey，无需辅助功能权限）
```

mac 的权限模型里，「监听全局键盘」通常需要用户在系统设置里手动授予「辅助功能」权限；而 Carbon 这个古老的注册式 API 是个历史遗留的绿色通道——注册一个「按下组合键时给我发个事件」的热键，**不需要任何权限弹窗**。对一个桌面宠物来说，装完即用、不弹 scary 的权限对话框，体验完胜。

代价是 API 古老（C 风格），70 行里一大半是样板。我们直接看它最精华的注册调用：

```swift
let hotKeyID = EventHotKeyID(signature: OSType(0x4650_4554), id: 1)  // 签名 'FPET'
let status = RegisterEventHotKey(
    keyCode,          // 键码：kVK_ANSI_P = 字母 P
    modifiers,        // 修饰键：cmdKey | shiftKey = ⇧⌘
    hotKeyID,         // 我们自己定义的热键 ID（收到事件时用来认领）
    GetApplicationEventTarget(),  // 事件投递目标：本应用
    0,
    &hotKeyRef        // 输出：注册成功后拿到一个句柄，注销时要用
)
```

三个概念：

| 概念 | 说明 |
| --- | --- |
| keyCode | 物理键的编号。`kVK_ANSI_P` 是 P 键。为什么不用字符而用编号？因为同一个字母在不同键盘布局上位置不同，编号才是物理事实 |
| modifiers | 修饰键掩码。`cmdKey | shiftKey` 用按位或组合多个标志（第 01 篇讲过的位运算实战） |
| hotKeyRef | 注册凭证。`UnregisterEventHotKey(hotKeyRef)` 注销时必须归还，所以它是可选类型成员，类销毁时（`deinit`）记得注销 |

### 2.2 Unmanaged：Swift 与 C 之间传递「我自己」

HotkeyManager 是 Swift 类，但 Carbon 的回调是 C 函数指针——它不懂 Swift 的引用计数，只认识一个 `void*` 指针。把一个 Swift 对象交给 C 世界的标准姿势是 `Unmanaged`：

```swift
let handler: EventHandlerUPP = { _, _, userData in
    guard let userData else { return noErr }
    let manager = Unmanaged<HotkeyManager>.fromOpaque(userData).takeUnretainedValue()
    DispatchQueue.main.async {
        manager.onTrigger?()
    }
    return noErr
}
```

- `Unmanaged.passUnretained(self).toOpaque()`（注册时）：「给 C 一个指向我的指针，但不增加我的引用计数」。为什么敢不增加？因为这个指针的生命期被我们约束在「handler 注册期间」——类销毁前先注销 handler，指针就不会悬空。
- `Unmanaged<HotKeyManager>.fromOpaque(userData).takeUnretainedValue()`（回调时）：「把 C 还回来的指针翻译回 Swift 对象」。

这套模式在 PetView 的 DisplayLink 回调里你已经见过一次（第 05 篇），这是 Swift 调底层 C API 的通用套路，记住这个形状就好。

另外一个细节：回调可能在任意线程被调用，而触发热键要做的事（读引擎状态、改 UI）都必须在主线程。所以回调体第一行永远是：

```swift
DispatchQueue.main.async { manager.onTrigger?() }
```

**「回调回到主线程再碰 UI」是 GUI 编程的军规。**

### 2.3 热键的智能：一个键三个动作

AppDelegate 里只注册了一个热键，却实现了三个动作，靠的是查状态机：

```swift
hotkey.onTrigger = { [weak self] in
    guard let self else { return }
    switch (self.engine.phase, self.engine.session?.kind) {
    case (.idle, _):
        self.startFocus()
    case (.running, .focus?):
        self.pauseSession()
    case (.paused, .focus?):
        self.resumeSession()
    default:
        break   // 休息中：什么都不做
    }
}
```

这是对第 08 篇状态机的直接应用：快捷键不做决定，它只查询状态机然后翻译成对应的引擎调用。`switch` 对元组（`phase` 和 `kind` 的组合）做模式匹配——Swift 的模式匹配能一次拆两个值，`.focus?` 里的问号是在匹配「session 存在且 kind 是 focus」。

## 三、系统通知

### 3.1 现代 API：UserNotifications 框架

发一条系统通知的代码在 AppDelegate 的 `notify(title:body:)` 里，拆开看是四步：

```swift
let content = UNMutableNotificationContent()
content.title = title
content.body = body
content.sound = .default
let request = UNNotificationRequest(
    identifier: UUID().uuidString,   // 每次随机 ID → 通知永远不会被去重
    content: content,
    trigger: nil                     // nil = 立即发送
)
UNUserNotificationCenter.current().add(request)
```

`identifier` 用 UUID 是个实用小技巧：系统会用 identifier 去重「同 ID 的待展示通知」。如果固定一个 ID，连续完成两轮专注时，第二条通知会替换掉第一条还没看的。随机 ID 让每条通知都独立展示。

### 3.2 环境探测：裸可执行文件别碰通知

这一行是血泪换来的：

```swift
/// 系统通知只有在正式 .app bundle 中才可用（swift run / Xcode 直接跑的裸可执行文件
/// 调用 UNUserNotificationCenter 会直接崩溃）
private var notificationsAvailable: Bool {
    Bundle.main.bundleURL.pathExtension == "app"
}
```

开发时你用 `swift run` 跑的是裸可执行文件，不是 `.app` 包。裸可执行文件调用通知中心会直接**崩溃**（不是报错，是 crash）。所以所有通知相关代码都裹在 `guard notificationsAvailable else { return }` 里。第 13 篇讲打包时会再解释 bundle 是什么——现在先记住：**判断「当前是不是正式 .app 环境」用 `Bundle.main.bundleURL.pathExtension == "app"`**。

首次启动还要请求授权：

```swift
UNUserNotificationCenter.current().requestAuthorization(options: [.alert, .sound]) { granted, _ in
    print("[FocusPet] 通知授权: \(granted ? "已允许" : "被拒绝")")
}
```

授权弹窗一生只会弹一次，之后用户在系统设置里改。回调里的 `granted` 告诉我们结果——但我们其实不需要据此改变行为：授权了通知能弹出，没授权就静默失败，应用本身照常运行。**「优雅降级」**：依赖的外部能力缺席时，核心功能不受影响。

## 四、三件套的分工总结

| 零件 | 类 | 核心技术 | 本章的坑 |
| --- | --- | --- | --- |
| 状态栏图标 | StatusBarController | NSStatusItem | accessory 应用要先 `NSApp.activate()` 再弹菜单 |
| 全局热键 | HotkeyManager | Carbon RegisterEventHotKey | C 回调用 Unmanaged 传 self；回调切主线程 |
| 系统通知 | AppDelegate.notify | UserNotifications | 裸可执行文件调用会崩溃，要探测 bundle |

注意这三件套共同的**结构模式**：每个零件都是一个「小类 + 回调插槽」，自己不管业务，业务全在 AppDelegate 接线。StatusBarController 不知道菜单里有什么；HotkeyManager 不知道 ⇧⌘P 会触发什么；通知不知道自己在庆祝什么。这种「零件只管能力，装配决定行为」的风格，让任何一件都可以单独替换（比如以后想把 Carbon 热键换成 `KeyboardShortcuts` 库，AppDelegate 一行不动）。
